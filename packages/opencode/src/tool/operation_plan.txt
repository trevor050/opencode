Write the execution-ready ULMCode operation plan.

Use this before broad execution. The plan must define ordered phases, concrete actions, success criteria, where subagents will be used, where they will not be used, assumptions, and the reporting closeout sequence. This is the durable operation order, not a vague checklist.

For pentest operations, plan depth must match the time budget:

- Under 2 hours: write a compact operation plan. Do not spend a large share of the budget on multi-layer planning.
- 2-8 hours: write a Discovery Charter first, record explicit operator approval, then write the full operation plan.
- 8-20 hours: use a Discovery Charter plus staged discovery/research lanes and explicit supervisor checkpoints.
- 20-36 hours: write a Discovery Charter that describes how to spend the first discovery/research/questioning window, get it approved, then write the full duration-aware overnight plan with supervisor handoff, orchestrator lane, recovery cadence, reporting closeout, and runtime daemon/scheduler strategy.
- More than 36 hours: require explicit operator confirmation that the run should continue beyond an overnight window.

The Discovery Charter is intentionally not the final execution plan. It is the plan for learning enough to write the real plan. It should say how to split the pre-plan time across research, passive/basic recon, tool inventory, scope questions, target classification, credential/safety questions, and candidate deep-work lanes. Its job is to give the operator something reviewable before the system commits to a 3h, 12h, or 36h operation order.

When the operator says credentials are available, use `operation_credentials` to create/list/get/materialize credential handles. Do not put raw usernames, passwords, tokens, or auth cookies in operation memory, evidence, findings, reports, command text, task metadata, or the operation plan. The durable plan may reference credential handles and authorized use, but not the secret values.

Do not write the actual full plan until the Discovery Charter has produced enough confidence that there is safe, useful, scoped work to fill the requested budget. The final plan must include `timeBudget.durationFit.confidence = duration_sized`, concrete evidence for that confidence, and an overflow backlog of safe work.

For long or overnight operations, run a Plannotator-style critique lane after the Discovery Charter and before approving the full durable operation plan when that lane is available. The critique must look for:

- missing scope, authorization, credential, safety, or reporting questions.
- lane gaps, weak dependencies, missing recovery cadence, and missing supervisor checkpoints.
- report closeout gaps, including report writer/reviewer, lint, render, runtime summary, and operation audit.
- ROE, safety, and non-destructive execution concerns.

Plannotator is a critic only. It may recommend questions or changes, but it does not replace native Build/Plan mode, does not replace this `operation_plan` tool, and does not become the durable plan of record.

Pentest plans should include these fields in the plan text even if the JSON schema is still represented as ordered phases:

- `planningMode`: `compact`, `discovery-charter`, or `full-duration`
- `durationBand`: `quick`, `standard`, `long`, `overnight`, or `extended`
- `questionsAsked`: the scope, authorization, safety, credential, duration, and reporting questions already answered
- `questionsDeferred`: questions intentionally delayed until discovery makes them useful
- `discoveryCharter`: the approved investment strategy for research, recon, operator questions, candidate deep-work lanes, and decision criteria before the real plan exists
- `planningApproval`: explicit approval status for the Discovery Charter before broad execution
- `timeBudget`: stage-by-stage allocation, duration-fit evidence, overflow backlog, and a finalization/reporting window
- `coverageContract`: coverage goals, minimum evidence thresholds, required lanes, allowed skips, retry/fallback rules, subagent opportunities, and report gates
- `supervisorHandoff`: when the supervisor reviews progress and what it is allowed to block
- `foregroundCommandPolicy`: confirmation that expected >2 minute commands go to supervised/background execution
- `reportCloseout`: report writer, report reviewer, report lint, report render, runtime summary, and operation audit sequence
- `districtAndPeopleRecon`: district profile, specific people/role profile lanes, identity graph construction, and how private/irrelevant information is excluded

The plan must design enough safe work for the requested budget: primary lanes, fallback lanes, retry lanes for timed-out scans, reporting lanes, and safe operator questions. It may finish early only when the coverage contract, report gates, runtime summary, and supervisor release all agree that no useful safe work remains.

Do not silently skip ambiguous work. A skipped or blocked lane needs a durable reason, coverage impact, and either alternate safe work or an operator question.

Do not use chat todos as the plan of record. The durable plan must be written here, then scheduled through `operation_schedule` before broad execution.
